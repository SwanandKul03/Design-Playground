# Design Playground

An interactive design-system project: explore colours and typography, try component variants, then arrange components, write and draw on a slate.

This is the exact source of the latest approved website. The HTML, CSS, JavaScript, five web fonts and 80 runtime colour values match the published version byte for byte. There is no framework conversion and no dependency on the original hosting service.

## Start in VS Code

1. Extract this archive and open the **design-playground** folder in VS Code.
2. Install Node.js 24 if Node is not already installed. Node 22 or newer is supported.
3. Open the integrated terminal in this folder and run:

~~~bash
npm run dev
~~~

4. Open **http://localhost:5173/** in your browser.

No npm install is needed; the server uses Node built-ins. Do not open dist/index.html by double-clicking: the colour data loads over HTTP. Edit the files in dist/ and refresh the browser. Stop the server with Ctrl+C.

VS Code also includes a **Start Design Playground** task and an **Open Design Playground** launch configuration. Press F5 to start the server and open the browser debugger, or use the terminal command above.

If the port is busy:

~~~bash
npm run dev -- --port 5174
~~~

Check JavaScript syntax:

~~~bash
npm run check
~~~

## Files to edit

| File | Purpose |
| --- | --- |
| dist/index.html | Page content, layout and editor controls |
| dist/styles.css | Styling, breakpoints, typography and component appearance |
| dist/app.js | Variants, properties, shared colour updates, slate interaction and local saving |
| dist/assets/tokens.json | The 50 primitive and 30 semantic button colours used by the site |
| dist/assets/fonts/ | All five fonts required to match the existing design |
| scripts/dev.mjs | Dependency-free local development server |
| reference/ | Your original design exports, font delivery archive and property screenshots |
| SOURCE_MANIFEST.json | File sizes and hashes linking the runtime copy to the approved source |

The dist folder contains editable application source; it is not generated by a build. No build step is required. The local server serves only dist/. Reference files are not part of the website.

## What is included

- Foundations: 50 colours, a type sample editor and the documented type scale.
- Buttons: Primary, Secondary and Tertiary; Large and Small; Default, Hover, Focused, Pressed and Disabled; left/right icon and text visibility.
- Inputs: four states with Default and Placeholder value types, label/helper/value visibility, and left/right/helper icons.
- Slate: add, select, drag, duplicate and delete components; add text; draw; change shared colours; undo/redo; switch between Arrange and Preview; zoom and fit.
- Small bracketed specifications reflecting the rendered examples.
- Browser-local saving. Nothing is submitted to a server.
- No top navigation, branding, export/import controls or original-sheet section. The footer contains only Back to top.
- Selected-colour information directly below the swatch instruction and above the palette.

A fresh browser starts with the four-item example. Local saving belongs to each origin: an existing composition on the hosted site does not automatically transfer to localhost or a GitHub Pages URL.

## Add the project to GitHub

Create an empty repository named **design-playground**. From this folder, initialise and commit the files:

~~~bash
git init -b main
git add .
git commit -m "Add Design Playground"
~~~

Copy the new repository's HTTPS URL from GitHub. Add it as the origin remote, then push the main branch. You can also use VS Code Source Control and Publish to GitHub.

Include the hidden .github and .vscode directories when copying the project. The ZIP contains both. No Git history, account credentials or hosting project configuration is bundled.

## Optional GitHub Pages deployment

A manually triggered GitHub Actions workflow is included in .github/workflows/pages.yml. It deploys only dist/; it does not deploy the reference exports.

Enable GitHub Actions as the repository's Pages publishing source, then run **Deploy Design Playground** from Actions. It does not publish automatically when you push code. The workflow works for a repository URL such as /design-playground/ because application assets use relative paths.

Official setup reference: https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages

## Source fidelity

Only the design-system collections in dist/assets/tokens.json drive the interface. The original token export is preserved in reference/tokens-original.json exactly as supplied, including its original encoding and unrelated collections. It is not loaded by the website.

The original export contains resolved colours, not recovered variable alias IDs, numeric variables, component layout metadata or full prototype actions. Browser bindings are explicit mappings. Small tertiary Default, Disabled and Pressed backgrounds follow the visual sheet where the raw export conflicts. Visitor overrides take priority. Input mappings use documented primitives.

The supplied heading font has a bold file only. Other heading weights are documented in the scale but are not synthesised in the live specimens. Runtime family aliases use generic names. Original reference files retain their original contents and metadata.

See ASSETS.md for the asset inventory. No licence has been invented for the supplied design or font files.
